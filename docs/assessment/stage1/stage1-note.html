Stage 1 — Accompanying note

Campus Device Loan System (Resource Center) · Afonso Caboz · Diagrams: C4 Context, C4 Container, Deployment

Intended MVP scope

  • Loan service (Rust API, PostgreSQL, outbox publisher) holds the authoritative state:
    • a public catalogue with available counts
    • reservations with a due date two days ahead
    • a waitlist for each device model
    • staff collection and return
    Row locks mean only one student can get the last unit.
  • Notifications service (Rust worker, Cosmos DB) sends collection and return confirmations. When a device comes back, it emails every student on that model's waitlist.
  • Web frontend (Next.js) gives visitors, students and staff the pages for these actions.
  • Deferred:
    • catalogue administration
    • deployed Staging and Production environments
    • real email in the demo; a fake sender records each delivery instead, so the full job lifecycle stays visible

Main technology choices

  • PostgreSQL because allocation needs locking and transactions. A transactional outbox stores each state change and its notification request in the same commit, so neither can exist without the other.
  • Azure Service Bus sits between the two services. It delivers each message at least once and moves failures to a dead-letter queue. The worker deduplicates by event ID, so a repeated message does not send a second email. Exactly-once delivery is not claimed.
  • Cosmos DB belongs to Notifications alone, holding delivery jobs and attempts. Neither service reads the other's database.
  • Rust (Tokio, Axum) for both backend processes: small images and fast start-up, which suit scale-to-zero.
  • Azure Container Apps provides managed TLS ingress, autoscaling on HTTP load and queue depth, and scale to zero.
  • Terraform defines every Azure resource, and GitHub Actions builds, tests and deploys.

Authentication, RBAC and personal data

  • Users sign in with Auth0 (OIDC authorisation code with PKCE). Next.js holds the session in an encrypted HttpOnly cookie, so access tokens never reach browser scripts.
  • The Loan API checks each RS256 JWT's issuer, audience, expiry and role claim:
    • students can reserve and join a waitlist
    • only staff can record collection and return
    • catalogue reads need no sign-in
  • Personal data is limited to the Auth0 user ID and the student's email. Both are stored with reservations and waitlist entries. The email is copied into notification requests only so it can be sent, and it is redacted in logs.
  • No passwords are stored anywhere. Azure services authenticate with managed identities, the database has no public endpoint, and the email API key is kept in Key Vault.

**Goal:** Produce four tidy draw.io C4 diagrams (Context, Container, Deployment, Stage 2 plan) that meet the CIS3039 brief and match the accepted Resource Center design.

**Architecture:** One `.drawio` source file with four pages, built with draw.io's built-in C4 shape library (`shape=mxgraph.c4.*`, `c4Type` user objects), the same library and palette as the Blackboard starter (`~/Downloads/C4_Flowchart.drawio`) and the user's reference screenshot. **Spec:** `/home/cabozzz/Downloads/cnd-cis3039-assessment-spec.docx` (Stage 1, Stage 2 and the Architecture & Design 25% rubric row). Design facts: `docs/architecture/adr/0002`–`0004`, `docs/backend/contracts.md`, `infra/workloads/main.tf`.

## Global Constraints

- Brief, Stage 1: "C4 Context and C4 Container diagram minimum; Deployment diagram recommended." Together they show users/actors, containers and responsibilities, technologies, connectivity direction, protocols, and deployment.
- Brief, Stage 2: a new diagram that starts as a copy of the Container diagram. It maps scenario requirements to containers, states auth/security per container, identifies faked/mocked connections, marks at least two software containers plus their essential stores as the MVP, and shows build order.
- Rubric, top band: "complete, precise, and professional"; realistic deployment for cloud scaling; clear security annotations, technologies and protocols; awareness of statelessness, async flows and resilience.
- Accepted design only. Nothing from the screenshot that ADRs 0002/0003 superseded: no Python FastAPI, no Nginx/Let's Encrypt, no Notifications→PostgreSQL edge.
- Boundaries: Loan owns PostgreSQL, outbox and publisher. Notifications owns Cosmos DB and Resend delivery. No edge between Notifications and PostgreSQL, and none between Loan and Cosmos DB.
- Infra values (replica ranges, ports, cron) come from `infra/workloads/main.tf`, not `docs/cloud/assessment-evidence.md`. That file is stale: it says web scales 0..2, but Terraform says 0..3.
- Status words stay honest. "Fake email in Test" and "Auth0 live sign-in pending" are labelled as such. Nothing claims exactly-once delivery.

## Tidiness rules (from the reference screenshot)

Every page follows these rules. Each task's visual check tests them.

1. Layout grid: people on the top row, the system boundary in the centre, external systems in a right-hand column, stores at the bottom. Main flow runs top to bottom.
2. Shapes: draw.io C4 library only. Person = `mxgraph.c4.person2`, web app = `webBrowserContainer2`, store = cylinder container, queue = horizontal-cylinder container. Standard palette: person `#083F75`, internal `#23A2D9`, external `#8C8496`, boundary dashed, no fill.
3. Box text: bold name, a `[Container: technology]` line, then one sentence of responsibility, at most about 14 words. Text never overflows a shape. The hexagon in the screenshot overflows; don't repeat that.
4. Edges: orthogonal routing (`edgeStyle=orthogonalEdgeStyle`), no diagonal lines, no edges crossing a box, at most one crossing per page. Label = bold verb phrase plus a `[protocol]` second line.
5. Uniform sizes: every container box is 240×120. Spacing snaps to a 40 px grid.
6. Each page has a title block at top-left (diagram name, scope, date) and a key at bottom-right that explains colours, dashed vs solid lines and any badges.
7. Ambiguity fix from the screenshot: the MVP marker is a dashed boundary that visibly encloses exactly the MVP containers. It is never a floating label.

## Review Focus

1. A reader checks the diagram against the ADRs. Any superseded tech (FastAPI, Nginx, Notifications→PostgreSQL) means lost marks: grep the XML for `FastAPI|Nginx|Let.s encrypt|Python` and expect no matches.
2. The tutor checks the Stage 2 page for requirement coverage. Every scenario requirement R1–R5 must appear on at least one container: grep each label.
3. A marker zooms the PNG. Text must stay legible at 100% in a PDF/report, so export at scale 2 and confirm the shortest side is at least 1600 px.
4. An operations reader checks scaling on the Deployment page. Each Container App shows a replica range and its scaler (HTTP for web/API, KEDA Service Bus for the worker, cron for the publisher).
5. Dark-mode or printed viewing. Exports use a white background (`-b white` / transparent off) so the dark text stays readable.
